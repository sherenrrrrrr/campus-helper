# 校园问卷互助平台交接说明

交接日期：2026 年 11 月 18 日。交接内容为 11 月 17 日完成的本地项目。

## 项目状态

仓库：https://github.com/sherenrrrrrr/campus-helper 。当前代码尚未提交或推送到 GitHub，交接包内文件是本地实际进度。不要只根据远程 README 判断进度。

已实现原生 HTML/CSS/JS 演示版：大厅筛选、问卷详情、发布及预算校验、模拟账号切换、领取、完成页图片上传、审核、申诉、管理员裁决、积分流水、时间推进及一键重置。管理员模块包含申诉、任务、用户、数据看板。数据只保存在 localStorage，不是真实身份、积分或后端服务。

小林、阿哲、管理员是主要演示账号，另有支持预置问卷的示例同学。普通账号只能在切换到管理员后通过头像菜单进入后台。切到管理员目前仍落在大厅，不会自动进入后台。

## 建议阅读顺序

1. README.md：打开方式和演示脚本。
2. docs/product-spec-v2.md：用户提供的 Claude 产品方案。
3. docs/schema.md：真实实现的数据结构和对方案矛盾的处理。

5. outputs/产品功能待办.md：用户后来补充的想法，仅记录，明确要求先不实现。

## 重要规则差异

- 首次发布的首份证明存疑时转管理员复核，不能直接拒绝；与产品方案验收中“首份直接拒绝”存在冲突，采用保护规则。
- 被拒绝后保留 7 天奖励额度和名额，申诉中继续保留，避免拒绝名额立即回流导致超卖或申诉发奖缺口。
- 停止或下架任务后，在途审核和申诉结清才退剩余预算，已通过的劳动报酬不回滚。
- 截图缩略图在同浏览器刷新后保留，结清 7 天后下次读取清理；不是刷新即消失。
- 积分守恒以及每个用户、任务、流水的对账，在纯函数 commit 后统一检查。

## 尚未解决或尚未实施

- 用户反馈“管理员后台没看到描述的内容”。代码中四个模块存在，已检查到用户当前为管理员账号、停留在发布页面；尚未完成入口可发现性及实际页面问题的排查和修复。不要把它说成已经修复。
- 匿名发布、问卷介绍截图或文件、减少手填、耗时保留、链接及其他字段预填，全部只有待办，没有实现。用户明确说“先不做”，需要新的实施指令后才能开发。
- 语音中“号史”暂理解为“耗时”，文档标为待确认；上传介绍材料应直接展示还是识别填表、预填来源是示例值还是自动提取，也未确定。

# 问问界面系统

工作模式：Operate。学生在教室、图书馆和宿舍用手机完成短任务；明亮环境下以浅色表面和深色文字保证可读。视觉采用克制的校园绿，表现主要操作、选中状态和积分到账；橙色对应待处理，红色对应拒绝和危险操作。

单一中文无衬线字体栈，优先本机可用字体，原型不依赖外部字体网络。字号 12/14/16/18/20/24/30/36，正文 16；标题不采用宣传页大字和渐变。最大容器 1248px，手机左右留白 20px。间距以 4/8/12/16/24/32/40 为主，面板圆角 16px，控件 8px。

四个主入口桌面为顶部导航，手机为固定底部导航。问卷详情和审核为层级页，头像负责切换模拟账号和演示工具。问卷卡片呈现主题、标题、耗时、奖励、已通过份数、可领份数和人群。积分中心分可用/冻结/累计获得，流水区分两个口袋。

所有动态数据如实标注演示；仅本地存储。状态变化用短暂反馈，减少动态效果，支持 reduced-motion、键盘焦点和原生 dialog 焦点约束。真实产品界面优先于营销技能里的全屏 hero、照片和滚动演出要求。

# 问问 · 校园问卷互助

面向单校学院或课题组的小规模互助演示。任务是找到适合自己的外部问卷、提交完成页证明赚取积分，用积分发布自己的问卷。一次招募 1～20 份，不服务大规模付费征样。

本次交付纯前端本地原型：三个主要模拟账号、16 份示例问卷、审核/申诉/管理员操作、时钟推进、积分流水、重置。未运行真实用户访谈，不宣称验证过产品假设。不实现真实注册、认证、邮件、后端或支付。

依据：用户提供的 product-spec-v2.md，规则冲突处理记录在 docs/schema.md。100 分启动积分、5～50 分奖励、24 小时领取、48 小时审核、7 天申诉、每日 5 份均为待试点验证默认值。

# 问问 · 校园问卷互助原型

按产品方案 v2 实现的本地演示，原生 HTML/CSS/JS，无运行依赖、无后端。所有账号和积分为模拟数据，不用于真实学生信息。

## 打开方式

直接双击 `outputs/campus-helper-demo.html`，无需安装环境。源码入口为 `prototype/index.html`，也支持直接双击。

推荐用本地服务保持稳定的存储来源：

```sh
node scripts/serve.cjs
```

浏览器打开 http://127.0.0.1:4173 。已有 npm 的环境也可用 `npm run dev`。本原型不依赖 npm 安装，当前机器直接运行 node 即可。

```sh
node --test tests/model.test.cjs
node scripts/build.cjs
```

build 同步生成单文件交付 `outputs/campus-helper-demo.html` 和静态部署目录 `dist/index.html`。修改源码后请重新 build，避免打开旧的单文件版本。

## 演示流程

1. 小林初始可用 100、冻结 0。发布“10 分 × 8 份”问卷，余额变为 20 / 80。示例链接可填写 `https://surveys.example/my-study`。
2. 再尝试发布超过余额的问卷，预算卡即时提示差额和按当前大厅奖励估算的答题数量，发布按钮禁用。
3. 右上角头像切换阿哲，领取小林的问卷，再单独点击打开问卷。示例链接展示本地说明；真实 http/https 链接在新标签页打开。
4. 阿哲提交 JPG/PNG 完成页截图，或者点击生成明确标注的演示证明，勾选隐私确认。积分暂时不动。
5. 切回小林，在“我发布的”找到待审核条数。可通过并发积分；首份证明存疑则说明原因转管理员复核。
6. 管理员头像菜单进入后台，裁决并填写理由。双方流水和处理记录更新，数据看板守恒等式保持成立。
7. 普通拒绝：先通过首份证明，再让另一位同学提交；之后可拒绝并由答题者 7 天内申诉。拒绝期间保留奖励和名额，避免超卖。
8. 头像菜单推进 49 小时，可以演示未审核自动通过；推进 25 小时可以演示未提交领取释放。推进只影响演示时钟。
9. 停止招募不立即退全部积分；在途提交、领取及申诉结清后退剩余预算。下架不回滚已通过奖励。
10. 头像菜单重置，恢复全部初始数据。可在 390px 宽度重复以上流程。

## 规则与分工

- `prototype/data/points.js`：纯状态转换和积分规则；`prototype/data/seed.js`：示例问卷和可对账历史。
- `prototype/app.js`：普通用户交互；`prototype/admin.js`：管理员队列、任务、用户、数据看板；`prototype/styles.css`：共享视觉。
- `docs/schema.md`：数据结构、积分不变量、v2 文档矛盾的处理依据。
- 产品文档中的团队分工是供人工协作参考，原型已按界面、规则、后台拆分，未替团队执行访谈或试点。

## 本地数据边界

localStorage 使用 `campus-helper-demo` key。截图压缩成本地缩略图，审核结清 7 天后下次读取清理，申诉中保留；重置立即清除本原型数据。刷新后保留，换浏览器、清除存储、切换 file/HTTP 入口会产生不同数据空间。浏览器禁止存储时显示临时模式，空间不足时阻止操作，不让界面显示虚假的成功。

首次证明保护、拒绝申诉名额保留等与 v2 验收文字冲突的选择，详见 `docs/schema.md`。自动发分、链接查重、风险标记等只为单浏览器演示；正式版必须由后端身份校验和数据库事务保证。多设备不同步，无真实学校认证或注册、无邮件通知、无问卷答案收集、无支付和积分提现。

## 下一步需要团队完成

找约 5 位发布者和 5 位答题者做访谈，再找 5 位同学无提示试用。记录能否 30 秒理解积分循环、哪一步卡住、是否接受截图审核。演示看板不代替真实试点证据。确定试点管理员、邀请范围和真实数据部署方案后，再另行规划正式版。

# 校园问卷互助平台 · 产品方案 v2

> 本文档基于 Codex 的初版设想修改完善。
> 原方案的框架是对的，这份文档保留它的骨架，重点补齐**它留白的地方**——那些"留待试点调整""不写死"的规则，如果不给默认值，原型根本演示不通。
>
> 文档内的每个数值都标注了性质：
> **【定】** 已决定，可以照做；**【原型默认】** 原型期先用这个数，试点后再改；**【待验证】** 需要真实用户反馈才能定，现在只给方案不给结论。

---

## 0. 先说结论：原方案哪里对，哪里必须改

**对的，不动：**
- "同一个账号两种角色"——这是这个产品的根本，比"发布者/答题者"分角色强得多，因为双向需求才撑得起互助。
- 优先解决外部问卷的完成确认——识别得准确，这确实是最大的产品难点，不是登录、不是界面。
- 先做演示原型、不接真实账号和真实积分——对，能省掉 80% 的工程量。
- 第一版不做充值提现、不做站内编辑器、不做聊天排行榜——边界克制得很好。

**必须改的，四个硬伤：**

### 硬伤一：审核超时没有默认值，整个闭环会断在这里

原文说"明确审核时限、逾期处理和申诉规则；不把这些尚未验证的规则写死"。

问题在于：**如果发布者永不审核，答题者的积分就永远冻结在"待审核"里。** 这不是一个可以留到以后再说的细节——它是原型能不能演示完整闭环的前提。第 6 节给了具体默认值（48 小时自动通过），并说明了为什么先偏向答题者。

### 硬伤二：没意识到"发布者白嫖"这个攻击路径

这是原方案最大的漏洞。截图审核里，发布者能看到截图，而截图里的完成页**可能包含答题者的答案**（尤其是问卷星、腾讯问卷这类，完成后常显示"您的答案已记录"加部分回显）。

于是出现一个零成本攻击：**发布者发任务 → 收满 10 份截图 → 全部拒绝 → 积分退回，但答案已经看完了。**

原方案只防了答题者作弊（重复领取），没防发布者作弊。第 6 节给了四层防御，其中"拒绝率异常检测"是原型就该有的。

### 硬伤三：积分循环没说清楚，用户看不出"为什么我要答"

原文说"第一批用户优先选择同时有发问卷和答问卷需求的"，这是对的洞察，但没把机制讲出来。

真实情况是：新用户拿 100 分启动积分，按 10 分 × 10 人发一次就用完了。**想再发，就必须先去答别人的问卷。** 这个"发一次就被迫去答"的设计其实是产品最精妙的地方，应该在引导里明说，而不是让用户自己发现。第 5 节把这条循环显式写出来了。

### 硬伤四：产品边界没划，会被"毕业论文 300 份"这类需求冲垮

一个要收 300 份样本的毕业论文，按每份 10 分算需要 3000 分——他得回答 300 份问卷，不可能。

**第一版只能服务"小额互惠"（单次 3～20 份），不服务"大规模征样"。** 这不是缺陷，是要写在明面上的定位。否则第一批用户里混进几个大样本需求，他们发布不了会直接流失，还觉得产品坏了。第 5.6 节给了处理方式。

---

## 1. 还需要你先回答的三个问题

这三个问题不回答，第 9 节的分工和第 12 节的验收标准都只能给一半。

**Q1 · 这个小程序是给哪个范围用的？**
- (a) 一个学院 / 一个课题组
- (b) 一整所学校
- (c) 跨校

> 影响很大：(a) 可以用邀请码甚至口头约定，管理员就是你自己；(b) 必须有真实注册和学籍核验；(c) 得做跨校认证，第一版别碰。**建议第一版锁在 (a)**，30～80 人的规模，靠邀请码就够，不需要写登录系统。

**Q2 · 谁来做管理员？**
- (a) 你自己（创始人兼管理员）
- (b) 轮值 / 招志愿者
- (c) 每院系一个管理员

> 影响申诉工作量。按 10 个任务/周的规模估算，每周大概 2～5 条申诉，一个人扛得住。**建议 (a)，但后台要留"管理员"角色字段，以后好扩展。**

**Q3 · 这个原型是给人看，还是给三个人接着写代码？**
- (a) 纯演示，投屏给人看，看完就扔
- (b) 演示 + 作为正式版的前端骨架

> 影响技术选型。**建议 (b)**，但按 (a) 的方式做——先用最轻的技术，能演示就行，别为了"以后要扩展"现在就上框架。见第 10 节。

---

## 2. 第一版要验证的假设（不是功能清单）

原方案列了要做什么，但没说**要验证什么**。原型的目的不是把功能做全，是回答下面三个问题。每个问题都对应一个可观察的行为：

| 假设 | 怎么算验证通过 | 怎么算证伪 |
|---|---|---|
| H1 · 学生愿意用积分互相帮忙填问卷 | 邀请 20 人，一周内至少 5 个任务完成闭环 | 一周内闭环 < 2 个 |
| H2 · 截图审核能被双方接受 | 审核纠纷率 < 20%，且没人因此退出 | 纠纷率 > 40%，或有人明确说"太麻烦不玩了" |
| H3 · 30 秒内能看懂"我要先答题才能发问卷" | 新用户首次进入，不提问也能说出这条规则 | 超过一半的人问"我的积分怎么来的/为什么发不了" |

**H3 是最容易失败的一个。** 建议在原型首屏就放一句话（不是教程页，是首屏文案）：*"发问卷要花积分，积分靠回答别人的问卷赚。"*

## 3. 业务闭环（重写，带状态）

原方案描述了流程，但没有状态定义。没有状态就没有"剩余名额怎么释放""任务什么时候算结束"这些必须回答的问题。

### 3.1 任务状态

```
                    发布（冻结积分）
                          │
                          ▼
      ┌────────────── 招募中 ◄──────────────┐
      │                   │                 │
   名额满              到截止时间         拒绝后名额回流
      │                   │                 │
      ▼                   ▼                 │
   ┌──────────────────────────┐             │
   │  待结算（还有未审核提交）  │─────────────┘
   └──────────────────────────┘
                  │ 所有提交审完
                  ▼
              已结束（退回剩余冻结积分）
```

**【定】五个状态：** `草稿`（可选，原型可跳过）→ `招募中` → `待结算` → `已结束`；任意时刻可 `已下架`（管理员强制，或发布者主动关闭）。

**【定】进入"待结算"的条件：** 名额已满 **或** 已过截止时间 **或** 发布者手动停止招募。此时**不再接受新的领取**，但已有的待审核提交必须处理完。

**【定】"已结束"的条件：** 待结算状态下，所有提交都已出结果（通过/拒绝/超时自动通过/申诉裁决完毕）。此时把未使用的冻结积分退回发布者。

> **这一条原方案没写，是最容易出 bug 的地方：** 如果任务关闭时直接退款，而那些还在"待审核"的提交后来通过了，就会退款余额不足或者重复发钱。必须先结算完所有在途提交，再退款。

### 3.2 提交状态（答题者侧）

```
   领取（占用一个名额，冻结 10 分）
        │
        ├── 24 小时内未提交 ──► 已释放（名额归还，无需任何操作）
        │
        ▼
     已提交（待审核）
        │
        ├── 发布者通过 ─────► 已通过（积分到账）
        ├── 发布者拒绝 ─────► 已拒绝（名额归还，答题者可申诉）
        └── 48 小时未审核 ──► 自动通过（标注"超时自动通过"）
                                  │
                        已拒绝 ───┴──► 申诉中 ──► 已裁决（管理员）
```

**【原型默认】领取后 24 小时未提交自动释放**——否则有人点"领取"占名额却不动手，名额就废了。

**【定】每人每个任务只能有 1 条提交记录**，包括被拒绝的。防止"被拒了换个号再来"和"反复提交刷概率"。

### 3.3 关键交互：三个"名额"的概念要分清

原方案混用了"名额"这个词，实际有三层，界面上必须区分：

| 概念 | 含义 | 大厅显示 |
|---|---|---|
| **总名额** | 发布时填的招募数量 | `共 10 份` |
| **已领取** | 有人领了但还没提交 | 不显示具体数，只在详情页显示 `剩 3 份可领` |
| **已完成** | 审核通过的数量 | `已收 7 份` |

> **建议大厅卡片显示：`已收 7 / 10 份`，并配一个进度条。** 答题者最关心的是"还值得点进去吗"，而"已领取但未提交"对他是噪音——但对发布者是重要信息，所以在详情页对发布者单独显示"3 人已领取，等待提交"。

## 4. 核心页面与信息架构

原方案列了五个页面，但没说导航怎么放。五个 tab 在手机上挤不下。

**【定】底部导航四个 tab + 右上角头像：**

```
┌─────────────────────────────────────┐
│  [头像]                        ← 我 / 演示重置 / 管理员入口 │
├─────────────────────────────────────┤
│                                     │
│           页面内容                   │
│                                     │
├─────────────────────────────────────┤
│  大厅    发布    我的任务    积分    │
└─────────────────────────────────────┘
```

`问卷详情`不是 tab，从大厅点进去的层级页面。`管理员后台`从头像菜单进，只有管理员账号看得到入口。

### 4.1 逐页要点（补齐原方案没写的交互细节）

**① 问卷大厅**

- 顶部筛选：主题 / 目标人群 / 预计耗时（≤3 分钟、3～5 分钟、5 分钟以上）
- 卡片信息层级（**顺序很重要**，按用户决策顺序排）：
  1. 标题
  2. `预计 3 分钟 · 奖励 10 分`
  3. `已收 7/10 份` + 进度条
  4. 目标人群标签（如"计算机学院 · 大三及以上"）
- **【定】默认排序：剩余名额多 + 奖励高优先，快满的不优先推**——因为快满的任务点进去大概率发现领不了，是坏体验。
- **【原型默认】已满/已截止的任务默认隐藏**，筛选项里可以打开"看已结束的"。
- 空状态必须有：`还没有问卷。要不你先发一个？` 加一个发布按钮。**原方案漏了空状态**，而冷启动场景下这会是大厅的默认样子。

**② 问卷详情**

必须回答答题者的四个问题，缺一个他就不敢点：

1. **要花多久？** → `预计 3 分钟`（发布者填，答题者可以事后评"实际用时"，但第一版只展示）
2. **奖励多少？** → `完成后 +10 积分`
3. **还领得到吗？** → `剩 3 份可领`
4. **我要做什么？** → 完成步骤三行：`① 打开问卷 → ② 填写并提交 → ③ 回来上传完成页截图`

**【定】按钮文案分四种状态**，原方案只说"查看要求"，太笼统：

| 状态 | 按钮 | 说明 |
|---|---|---|
| 可领取 | `领取并开始`（主按钮） | 点击后占用名额，跳到外部链接 |
| 已领取未提交 | `去提交证明` | 展示剩余时间倒计时 |
| 已提交待审核 | `审核中`（禁用） | 显示"预计 48 小时内出结果" |
| 已完成 | `已完成 · +10 分`（禁用） | 绿色状态 |

**【定】外部链接不能自动跳转。** 必须先点"领取"，再点"打开问卷"，并且用一个明显的过渡提示：`问卷在新页面打开。填完记得回来提交截图。` 否则用户填完就关掉，再也想不起来回来。

**③ 发布问卷**

原方案说"预览积分预算"，但没说清什么时候校验、校验什么。**【定】分三步：**

1. **填信息**：标题（≤30 字）、说明、目标人群、预计耗时、外部链接、单份奖励、招募数量
2. **实时预算卡**（一直显示在页面底部，不是单独的预览页）：
   ```
   冻结 10 × 8 = 80 分
   当前可用 100 分  →  发布后剩余 20 分
   ```
   **积分不足时：** 预算卡变红、主按钮禁用、并给一句可操作的提示：`还差 30 分。去大厅答 3 份问卷就够了。`（带跳转，别只说"积分不足"）
3. **提交**

**【定】必填校验在第一步就做，不要等点了发布才报错。** 尤其是：
- 链接必须是 http/https 开头
- **链接查重**：同一链接已存在时拦截，提示"这个问卷已经有人发过了"。这条是防刷分的关键，见 11.2
- 招募数量 1～20（原型阶段上限，防止大样本需求进来）
- 单份奖励 5～50

**④ 我的任务**

原方案把"已发布"和"已参与"放一个页面，但没说怎么分。**【定】两个 tab：**

- **我发布的**：每条显示 `已收 7/10 · 待审核 2`，有 `去审核` 入口。**待审核数量要对发布者可见并醒目标记**，否则他不会想起来去审。
- **我参与的**：每条显示状态标签，被拒绝的要有 `申诉` 按钮。

**发布者审核页（从"我发布的"进）：**
- 展示：答题者昵称、提交时间、截图（可放大）、补充说明
- 两个按钮：`通过` / `拒绝`
- **【定】拒绝必须选原因**（下拉：截图不清晰 / 看不出完成 / 未按要求填写 / 其他+文字），原方案说了"拒绝时必须填写原因"，但没说形式——自由文本框会导致申诉时扯皮，结构化原因才能进统计、才能做 6.4 的拒绝率检测。

**⑤ 积分中心**

**【定】必须分区，不能只显示一个总数：**

```
可用 82 分      冻结 80 分      累计获得 160 分
─────────────────────────────────
流水
  10-24  +10  完成「实习经历调研」       已到账
  10-24  -80  发布「毕业去向问卷」        已冻结
  10-20  +100 新用户启动积分
```

流水每行要有：**时间、金额（正负）、原因、对手方/关联任务、状态**。原方案说"积分必须有流水，展示获得、冻结、支出和退回的原因"，这是对的，这里把它具体化成可实现的字段。

**【定】冻结的积分也要在流水里出现**，标注"已冻结"，任务结束后再出一行"退回"。否则用户会以为钱丢了。

**⑥ 管理员后台**

原方案只说了"申诉处理和违规任务下架"。见第 8 节，这里展开。

## 5. 积分系统（完整规则）

### 5.1 记账原则

**【定】积分总量守恒。** 系统里积分的唯一来源是"新用户启动积分"，此外**只能转移，不能创造**。管理员调账是唯一例外，且必须留痕。

这条原则的好处：任何一个时刻，`所有用户的可用余额总和 + 冻结总和 == 100 × 注册用户数 + 管理员调账净额`。**这是个可以写进验收测试的等式**，能抓出几乎所有记账 bug。

**【定】每笔变动都要有对手方。** 不是"张三 -80"，而是"张三 -80 → 冻结到任务 #12"。正式版用复式记账（两条记录，一借一贷），原型阶段至少保证"变动金额 = 流水条目之和"。

### 5.2 余额的两个口袋

| 口袋 | 含义 | 能不能花 |
|---|---|---|
| **可用余额** available | 现在就能用 | 能 |
| **冻结余额** frozen | 已被某个任务锁住 | 不能 |

**【定】不变量：** `available ≥ 0` 且 `frozen ≥ 0`，任何时刻都不允许为负。

### 5.3 数值（原型默认值）

| 项目 | 值 | 性质 |
|---|---|---|
| 新用户启动积分 | 100 | 【原型默认】试点后可调 |
| 单份奖励默认值 | 10 | 【原型默认】 |
| 单份奖励允许范围 | 5 ～ 50 | 【原型默认】 |
| 单任务招募数量上限 | 20 | 【原型默认】防大样本需求 |
| 领取后提交时限 | 24 小时 | 【原型默认】 |
| 发布者审核时限 | 48 小时，超时自动通过 | 【原型默认】见 6.3 |
| 每日最多提交 | 5 份 | 【原型默认】防刷分 |
| 申诉时限 | 被拒绝后 7 天内 | 【原型默认】 |

> **为什么启动积分是 100：** 刚好够"10 分 × 10 人"发一次。发完就没了，用户自然会发现要先去答题。这个数字不是随便定的，它承担了引导功能。别改成 1000，那样用户能连发十次，永远不用答题，循环就断了。

### 5.4 一笔钱的完整生命周期

以"发布 10 份 × 10 分"为例（发布者和答题者 A 初始都是 100 分，两人总计 200 分，全程守恒）。

**分支 A · 审核通过**

| 步骤 | 发布者 可用 | 发布者 冻结 | A 可用 | 流水条目 |
|---|---|---|---|---|
| 初始 | 100 | 0 | 100 | — |
| 发布 | 0 | 100 | 100 | `-100 发布冻结` |
| A 领取 | 0 | 100 | 100 | —（不动钱，只占名额） |
| A 提交 | 0 | 100 | 100 | —（不动钱） |
| 审核通过 | 0 | **90** | **110** | `A +10 任务奖励`；`发布者 冻结 -10` |
| 任务结束（用了 1 份，剩 9 份） | **90** | **0** | 110 | `+90 剩余退回` |

**分支 B · 审核被拒（同样从"发布"之后开始）**

| 步骤 | 发布者 可用 | 发布者 冻结 | A 可用 | 流水条目 |
|---|---|---|---|---|
| A 提交 | 0 | 100 | 100 | —（不动钱） |
| A 被拒 | 0 | **100** | **100** | —（额度留在冻结池，名额 +1 回到 10） |
| 任务结束（一份没用） | **100** | **0** | 100 | `+100 剩余退回` |

**两个实现时最容易搞错的点：**

1. **被拒绝时，额度退回的是"冻结池"，不是可用余额。** 因为名额重新开放了，这 10 分还得继续为这个任务冻结着。原方案没写这条，写成"退回发布者"会直接导致余额算错。
2. **只有审核"通过"才真正从冻结转出。** 领取、提交、被拒都不动钱，只动名额。

两条分支结束时两人总额都是 200 分，可以据此写断言测试。

**如果任务在还有待审核提交时就被关闭**，不能直接退款：必须先等所有在途提交出结果，再退剩余冻结（见 3.1）。否则会退款不足或重复发放。

### 5.5 积分能干什么（这条决定了整个系统的安全性）

**【定】积分不可提现、不可转让给个人、不可兑换任何实物或现金，只能用于在本平台发布问卷。**

这不是"第一版暂时不做"，而是**必须长期坚持的设计**。理由：

> 如果积分能换钱，那么截图审核必然被攻破——作弊收益大于成本，任何弱审核都挡不住。积分越"没用"，作弊动机越低。这条规则是截图审核能成立的前提，写进用户协议。

### 5.6 明确不服务的需求（边界声明）

| 需求类型 | 第一版怎么处理 |
|---|---|
| 要收 50～300 份的毕业论文 | **不支持。** 发布页提示"单次最多 20 份，大样本需求请联系管理员" |
| 需要特定人群（如"只限女生""只限大四") | 支持标注，但**资格靠自述 + 发布者审核把关**，不做硬性核验（见 6.5） |
| 愿意付费买积分 | **不支持。** 这是有意的限制，不是缺口 |

**这里有个战略问题要留给你想：** 如果平台只服务"小额互惠"，那它的天花板就是"帮同学互填问卷"，长不成更大的东西。如果以后要服务毕业论文这种真实大需求，就必须引入付费——而这会破坏 5.5 的安全性。

**这两个目标是冲突的，现在不用解决，但要知道自己选哪边。** 我的建议：第一版明确站在"互惠"这边，把"大样本"当作未来可能的第二产品线，用独立的产品形态（比如付费的样本招募服务）去做，不要污染互助社区的积分体系。

## 6. 外部问卷的完成确认（最难点，给具体方案）

原方案定了方向（截图 + 人工审核 + 申诉），但关键参数全是留白。这节补齐。

### 6.1 为什么这个真的难

一句话说清：**"完成"这个事实发生在别人的服务器上，我们只有间接证据。**

三种证据各有致命缺陷：

| 证据 | 能证明什么 | 不能证明什么 |
|---|---|---|
| 用户说"我填完了" | 什么都不能 | 一切 |
| 打开了链接 | 点过链接 | 是否真的填、是否有效 |
| 完成页截图 | 大概率填完了 | 可能造假、可能填了被筛掉（无效样本） |

**【定】接受这个现实：这不是要解决"绝对防作弊"，而是要作弊成本 > 收益。** 因为积分不可变现（5.5），作弊收益本来就极低。所以审核可以"松"，但要"可申诉"。

### 6.2 截图的具体要求（原方案只说"仅截取完成页"，太笼统）

**【定】上传规则：**
- 仅 1 张，JPG/PNG，≤5MB
- **必须在界面上明确要求：只截"提交成功/已完成"的提示页，不要截包含你答案的页面**
- 提示语要给出理由，否则用户不当回事：`截图只用于确认你完成了，不需要显示你填了什么。请只截完成页，保护你自己的隐私。`
- **【定】平台不做内容识别，只存图。** 不做 OCR，不读截图内容——技术上做不到可靠，且会引入隐私问题。

**【定】截图的生命周期（这条原方案完全没有）：**
- 审核完成后 **7 天自动删除**，只保留"审核结果"记录
- 用户注销时立即删除
- 存储位置：正式版用对象存储，原型阶段只在内存/localStorage 里放缩略图，明确标注"演示数据，刷新即消失"

> 这是个人信息保护的基本要求。问卷截图里可能有答题者的学院、年级、甚至姓名——存着不删是有风险的。

### 6.3 审核时限与超时（原方案留白的最关键处）

**【原型默认】48 小时未审核 → 自动通过，标注"超时自动通过"。**

为什么偏向答题者而不是退回：

- 答题者已经付出了劳动，让他等一个可能永远不来的审核，是最伤的体验
- 如果超时退回，发布者可以"拖死"所有提交，等于零成本白嫖（配合硬伤二）
- 自动通过的最坏后果是发布者损失 10 分——而这 10 分本来就是他承诺要付的

**【定】发布者的保护措施：** 如果确实遇到恶意提交（比如传了一张无关图片），可以在自动通过后 **7 天内申请管理员介入**，管理员核实后可回滚并扣回答题者积分。这保留了纠错能力，又不让答题者承担等待成本。

**超时前要有提醒**，否则发布者会觉得"我被坑了"：
- 剩余 24 小时：站内提醒
- 剩余 6 小时：再提醒一次
- 界面文案：`还有 2 份待审核，48 小时后将自动通过`

### 6.4 防"发布者白嫖"（原方案的漏洞，四层防御）

| 层 | 措施 | 说明 |
|---|---|---|
| L1 · 减少信息泄露 | 截图要求只截完成页 | 从源头减少答案泄露 |
| L2 · 提高攻击成本 | 首次发布的用户，**第一份提交必须通过** | 新手不能一上来就拒绝所有人 |
| L3 · 异常检测 | 拒绝率 > 50% 且拒绝数 ≥ 3 → 标记"高风险发布者" | 进管理员队列，同时该任务后续提交**改为自动通过** |
| L4 · 事后追责 | 管理员可回滚已发放积分、下架任务、限制发布权限 | 留痕，多次违规封号 |

**【原型默认】L2 和 L3 是必做的**，因为不加的话，演示时如果有人故意演示恶意路径，流程会直接崩掉。L4 靠管理员后台手动做。

### 6.5 参与资格怎么判定（原方案说"查看参与资格"，但没说怎么判）

原型阶段**没有任何可信的身份系统**，所以：

**【定】资格是"软约束"：**
- 发布者填"目标人群"是自由文本 + 标签（如 `计算机学院`、`大三及以上`、`有实习经历`）
- 答题者自己判断符不符合，点"领取"即视为自述符合
- **真正的把关发生在审核环节**：发布者看到提交，如果明显不符合（比如要求"有实习经历"但答题者说明里写"我没实习过"），可以拒绝并选原因"不符合目标人群"

**【定】不要做硬性过滤。** 比如不要做"只允许计算机学院看到"，因为：① 没有可信的院系数据；② 用户可能跨院选课；③ 拦截了人反而让任务招不满。

界面上要说清楚这件事，避免答题者觉得被骗：详情页显示 `此问卷希望由「计算机学院 · 大三及以上」的同学填写，请自行确认是否符合。`

### 6.6 申诉流程（原方案只提了一句）

```
答题者被拒 ──► 7 天内可申诉（必填申诉理由）
                    │
                    ▼
              进入管理员队列（标注"申诉"）
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
   维持拒绝      判答题者胜    判双方无责
   （名额不还）  （积分补给     （任务下架，
                  答题者）      双方退回）
```

**【定】申诉期间积分状态：** 额度保持冻结，不发放也不退回。避免"先发了再追回"的麻烦。

**【定】管理员裁决必须写理由**，双方都能看到。这是信任的基础——用户不怕被拒，怕的是不知道为什么不公。

**【原型默认】申诉由管理员 3 个工作日内处理。** 超过就说明管理员扛不住了，该考虑加人或改规则。

## 7. 账号与注册（你问的，原方案完全没写）

这是原方案最大的空白。分三个阶段，**不要把三阶段的方案混在一起做**。

### 7.1 阶段 0 · 演示原型（现在）

**【定】不做注册。预置三个模拟账号，右上角一键切换。**

| 账号 | 角色 | 初始状态 |
|---|---|---|
| 小林 | 普通用户 | 可用 100 分，已发布 1 个任务（用于演示审核） |
| 阿哲 | 普通用户 | 可用 60 分，冻结 40 分，有 1 条待审核提交 |
| 管理员 | 管理员 | 可见后台入口 |

**为什么这么做：** 演示的关键是"能一键切换角色看两边"，而不是"能填手机号收验证码"。真实注册在演示里只会增加故障点。

**必须有：** 头像菜单里的 `重置演示数据`，一键恢复初始状态。原方案提了"提供一键重置"，这里落实了。

### 7.2 阶段 1 · 小规模试点（20～80 人）

**【定】邀请码 + 手机号验证码（或邮箱验证码），二选一即可，不要两个都要。**

推荐 **邀请码 + 邮箱验证码**：

| 组件 | 做法 | 为什么 |
|---|---|---|
| 邀请码 | 一次性或限次（如每码 10 次），管理员后台生成 | 控制规模、挡住校外人员、控制积分通胀（积分总量 = 100 × 人数） |
| 邮箱验证码 | 6 位数字，10 分钟有效 | 免费、不用备案、比手机短信省事省钱 |
| 昵称 | 用户自填，2～12 字，平台内唯一 | **不要用真名**，降低隐私风险 |
| 学院 / 年级 | 选填下拉，仅用于人群标签匹配 | **不做核验，只做标签** |
| 学号 | **不收集** | 见 7.4 |

**手机号 vs 邮箱，为什么建议邮箱：** 短信要资质、要付费、要防刷，试点阶段没必要。邮箱验证码用 Resend / 阿里云邮件推送之类，几百人的量成本几乎为零。**缺点**是学生不常看邮箱——所以要在注册页写清楚"验证码会发到邮箱，去垃圾箱看看"。

**为什么一定要邀请码：** 不只是控规模。**积分总量 = 100 × 注册人数，人越多通胀越厉害**（虽然总量守恒，但人多了每个任务能分到的答题者不变，而任务数会增加）。邀请码是最简单的阀门。

### 7.3 阶段 2 · 正式版

**【定】接学校统一身份认证（CAS / OAuth2），不要自己做密码登录。**

理由：
- 学校有现成的、可信的学籍数据，能真正解决"他是不是本校学生"
- 自己做密码系统意味着要存密码哈希、做找回、做防撞库——成本高且风险大
- 统一认证通常一步完成"注册 + 实名 + 院系"

**在此之前，绝对不要让学生用学号和自设密码登录。** 学生会习惯性用教务系统密码，一旦这个平台被拖库，学生的手续密码就泄露了——这是真实会发生的安全事故，责任在你们。

### 7.4 合规与隐私（学生场景必须考虑，一段话讲清）

| 事项 | 做法 |
|---|---|
| 收集什么 | 邮箱、昵称、学院年级（选填）。**不收集身份证、学号、真实姓名、位置** |
| 告知同意 | 注册时必须勾选同意《用户协议》《隐私政策》，用大白话写清"我们存什么、存多久、给谁看" |
| 问卷答案 | **平台永远不存问卷答案**，答案在第三方问卷平台上，不在我们这 |
| 截图 | 见 6.2，审核后 7 天删除 |
| 注销 | 必须提供，注销即删数据（未结清的积分随之作废，要提前告知） |
| 数据出境 | 不要用境外服务存用户数据 |

> 一句提醒：如果这个平台是作为**课程项目或学生组织项目**做的，风险相对小；如果以后要作为**正式服务**运营，在境内提供服务需要做 ICP 备案（服务器在境内）。如果你用 Cloudflare Workers + D1 这种境外架构，就不适合存真实学生数据。这个决定要在试点前想清楚。

### 7.5 三种注册方式对比（供你选）

| 方式 | 试点成本 | 安全性 | 何时用 |
|---|---|---|---|
| 邀请码 + 邮箱验证码 | 低 | 中 | **推荐用于试点** |
| 邀请码 + 手机号验证码 | 中（要资质/费用） | 中 | 需要更强唯一性时 |
| 学校统一认证 | 高（要申请对接） | 高 | 正式版 |
| 微信登录 | 中（要小程序主体） | 低（拿不到学籍） | 不建议单独用 |
| 学号 + 自设密码 | 低 | **低（有风险）** | **不要用** |

### 8.1 申诉队列（最重要）

- 列表：任务标题、答题者、拒绝原因、答题者申诉理由、拒绝时间、剩余处理时限

### 8.2 任务管理

- 操作：`强制下架`（填原因，通知发布者，退回冻结积分）、`延长截止时间`

- 列表：昵称、注册时间、积分、发布数、完成数、拒绝率、违规次数

必须有的 6 个数字：
1. 注册用户数 / 7 日活跃
2. 任务发布数 / 完成数（**闭环率是核心指标**）
3. 平均审核时长
4. 拒绝率 / 申诉率
5. 积分总量（校验 5.1 的守恒等式）
6. **卡在哪：** 领取后未提交的比例、发布后无人领取的任务比例

> 第 6 项是原方案完全没提的，但它才是原型阶段最该看的东西——**"卡住的位置"比"页面好不好看"重要**，这正是你在原文第 5 节写的那句话的意思。把它变成可看的数字。

## 9. 三个人的分工（你问的）

**先说一个现实问题：** 原型阶段三个人的分工不能按"功能"切，会互相等。UI 设计那位不出稿，另外两人就没法动手；登录那位在原型阶段基本没事干（因为不做真登录）。

**【定】按"产出物"切，并且明确先后顺序：**

### 9.1 角色与产出

| 角色 | 原型阶段产出 | 依赖谁 | 什么时候能开工 |
|---|---|---|---|
| **A · UI / 交互设计** | ① 五个页面的手机端高保真稿（Figma 或直接 HTML）② 组件库（按钮/卡片/状态标签/空状态）③ 全部文案 | 无，**第一个开工** | 立刻 |
| **B · 数据与规则** | ① 数据模型（JSON schema）② 积分记账函数 ③ Mock 数据集 ④ 标签体系 + 链接查重规则 | A 的页面结构 | 第 2 天，可以和 A 并行 |
| **C · 账号与后台** | ① 模拟账号切换器 ② 管理员后台四块界面 ③ 登录方案调研（试点/正式版） | A 的组件库 | 第 3 天 |

### 9.2 三个人怎么不打架

**原型阶段的最大风险是三个人同时改一个 index.html。**

**【定】分工到文件，不分工到功能：**

```
campus-helper/
├── docs/                    ← 全员只读
├── prototype/
│   ├── index.html           ← A 独占（结构 + 样式）
│   ├── data/
│   │   ├── schema.md        ← B 独占（数据模型定义）
│   │   ├── seed.json        ← B 独占（Mock 数据）
│   │   └── points.js        ← B 独占（积分逻辑，纯函数）
│   ├── app.js               ← A 定骨架，B 接数据，C 接后台
│   └── admin.js             ← C 独占（管理员界面）
└── README.md                ← A 维护演示脚本
```

**关键：`points.js` 里全是纯函数**（`freeze(balance, amount)`、`settle(task, submission)`），B 写完可以单测，谁都能调，不会冲突。

### 9.3 第一天必须先对齐的一件事

**【定】三个人花 1 小时一起定"数据模型"，写进 `docs/schema.md`，之后 3 天内不许改。**

因为所有三个人都依赖它：A 要知道卡片上显示什么字段，B 要写规则，C 要做后台列表。这是唯一必须坐在一起做的事，其他都能并行。

最小数据模型（这个可以照抄）：

```js
// 用户
{ id, nickname, avatar, role: 'user'|'admin', 
  available: 100, frozen: 0, createdAt }

// 任务
{ id, publisherId, title, description, audience: [tag,...],
  minutes, link, reward, quota, 
  status: 'open'|'settling'|'closed'|'removed',
  deadline, createdAt }

// 提交
{ id, taskId, userId, status: 'locked'|'pending'|'approved'|'rejected'|'appealed',
  screenshot, note, rejectReason, createdAt, submittedAt, resolvedAt }

// 流水
{ id, userId, delta, type: 'grant'|'freeze'|'unfreeze'|'transfer'|'refund'|'adjust',
  taskId, submissionId, note, createdAt }
```

### 9.4 一句话评价这个分工

**三个人做这个原型其实是偏多的。** 原型总共大概 1500～2000 行代码，一个人 3～4 天能做完。三个人如果协调不好，会因为接口对齐耗掉更多时间。

**如果一定要三个人，建议：** A 和 B 实打实干活，C 的时间主要花在"调研正式版的登录方案 + 做后台界面"上——因为后台在原型阶段可以很简陋，但登录方案调研是真有价值的准备工作。

## 10. 原型的"数据清洗"到底指什么（你说的人）

"数据清洗"这个词在产品语境里有三种可能，我猜你指的是第一种，但三种都列一下，因为它决定这个人的产出：

| 解释 | 具体工作 | 原型阶段价值 |
|---|---|---|
| **① 内容清洗**（推荐） | 问卷去重、垃圾任务识别、链接格式校验、失效链接检测、标签抽取与归并 | **高。** 直接决定大厅能不能用 |
| ② 试点数据分析 | 把用户反馈和看板数据整理成可读的结论 | 中。试点阶段才需要 |
| ③ 积分配对账 | 校验守恒等式、找异常流水 | 中。但应该是自动测试，不是人力 |

### 10.1 如果按 ① 做，这个人的具体产出

**【定】四件事，都是原型阶段就能做的：**

1. **链接规范化 + 查重**
   - 去掉 `?utm_source=...` 之类的追踪参数
   - 识别主流问卷平台（问卷星 `wjx.cn`、腾讯问卷 `qq.com`、金山 `jinshuju.net`、Google Forms、Credamo 等）
   - 同一链接归一化后重复 → 拦截
   - **为什么重要：** 同一份问卷被两个人发布，会变成互相刷分的工具

2. **标签体系（这个最容易被低估）**
   - 把自由文本的"目标人群"归并成有限标签：`学院`、`年级`、`专业方向`、`经历类型`
   - 例：用户写"计算机的大三大四"→ 标签 `[计算机学院, 大三, 大四]`
   - **有了标签，大厅的筛选才真的能用。** 否则筛选框里全是"随便""都行""同学们"
   - 原型阶段可以先做人工归并 + 一个固定标签表

3. **Mock 数据集**
   - 造 15～20 条"看起来真实"的问卷（真实的学生会问什么：实习经历、考研意向、食堂满意度、宿舍作息、课程评价）
   - **标题和说明要真的像学生写的**，不要写"测试问卷 1"
   - 这是演示效果的关键——**演示能不能打动人，一半取决于 Mock 数据像不像真的**

4. **垃圾任务识别规则**
   - 标题过短（< 5 字）、说明空白、奖励异常高（> 50）、链接打不开
   - 命中 → 发布时提示，或进管理员待审队列

## 11. 原型技术选型

**【定】建议：单文件 HTML + 原生 JS + localStorage，不用框架。**

理由：
- 三个人的协调成本，在框架项目里会翻倍（依赖、构建、配置冲突）
- 演示只需要"能点、状态能变、能重置"，不需要工程化
- 交付物是**一个可以直接双击打开的 html 文件**，发给任何人就能看，不用装环境

**但如果你选 Q3 的 (b)（当作正式版骨架）**，那建议 Vite + React + TypeScript，因为正式版必然要这个。**代价是原型工期从 3 天变成 6～8 天。**

**【定】两种都不要做的：**
- Next.js 全栈 + 数据库（原型不需要后端）
- 微信小程序（要先注册主体、审核，原型阶段不值得）

### 11.1 状态管理（原型的核心技术点）

```
localStorage['campus-helper-demo'] = {
  users: [...], tasks: [...], submissions: [...], ledger: [...],
  currentUserId: 'u1',
  version: 1
}
```

**【定】所有写操作走同一个函数**：`commit(action)` —— 统一写入、统一加流水、统一保存。这样：
- 积分守恒可以在一处保证
- 一键重置就是 `commit({type:'reset'})`
- 以后换成真后端，只需要改这一个函数

### 11.2 防作弊的具体实现（原型阶段）

| 规则 | 实现位置 | 难度 |
|---|---|---|
| 一人一任务一次 | 提交前查 `submissions` 里有没有 `taskId+userId` | 简单 |
| 链接查重 | 归一化后比对现有任务的 link | 简单 |
| 每日提交上限 | 数当天 `submittedAt` 的条数 | 简单 |
| 领取超时释放 | 每次读取时惰性计算（不用定时器） | 简单 |
| 拒绝率检测 | 审核时实时算 | 简单 |

> **全部都能在前端做**，因为原型只有一个用户在用。但要在文档里写清：**正式版这些必须放后端**，前端校验只是体验优化。

## 12. 可测的验收标准（替换原方案第 5 节）

原方案说"原型至少能够完整演示"，但列的条件不够可测。下面每条都能勾选：

### 12.1 演示脚本（照着走一遍，全过才算达到）

**【定】这是演示时你要走的顺序，也是验收清单：**

| # | 操作 | 期望结果 | 对应原方案 |

# 本地演示模型 v2

所有状态变动进入 `CampusModel.commit(previous, action, timestamp)`，返回新状态，失败抛出明确错误，原状态不变。页面仅在成功写入 localStorage 后替换内存状态。

状态包含 users、tasks、submissions、ledger、notices、audit、currentUserId、now、timeOffset、sequence、version。账号仅为模拟，不提供真实鉴权。

- User：id、nickname、role、available、frozen、createdAt、lastActiveAt、restrictedUntil、banned、violations。
- Task：id、publisherId、title、description、topic、audienceText、audience、minutes、link、reward、quota、escrow、deadline、createdAt、stopped、status、reports、removalReason。
- Submission：id、taskId、userId、status、createdAt、claimUntil、submittedAt、reviewUntil、resolvedAt、appealUntil、screenshot、note、history、final、automatic、reminded、challenge。
- Ledger：id、userId、availableDelta、frozenDelta、delta（可用变动兼容字段）、type、taskId、submissionId、counterparty、note、createdAt。

任务状态：open、settling、closed、removed。提交状态：locked、pending、approved、rejected、appealed、expired、cancelled、overturned。流水同时记录两个口袋，不能只把一列 delta 相加解释为总资产变化。

守恒：所有可用余额 + 所有冻结余额 = 100 × 用户数 + 管理员调账净额。每个用户余额等于其流水对应口袋之和；每个发布者冻结余额等于其任务 escrow 之和；在途提交的奖励必须被 escrow 覆盖；名额不能超卖。每次 commit 后都检查。

原型 action：switch、tick、advance、publish、claim、submit、review、appeal、challenge、judge、stop、remove、extend、manageUser、report、readNotices。reset 由存储边界重新生成 seed，保证只清除本原型的 key。正式版需要把这些操作迁移到服务端事务，不能直接上线本地模型处理真实数据。

## 对 v2 文档冲突的明确处理

1. 首次发布的首份证明保护优先于验收示例里的“第一份直接拒绝”。首次疑问转交管理员复核，不直接判无效。要演示普通拒绝，先通过首份，再提交第二位同学的证明。
2. 拒绝立即回流名额与“申诉期间保留额度”会产生超卖和申诉赔付缺口。这里拒绝后 7 天保留额度与名额；期满未申诉或管理员维持拒绝才释放。申诉中一直保留。任务停止后也必须等待结清，不提前退款。
3. 下架只取消未提交领取；已通过不回滚，待审和申诉继续处理，之后退剩余积分。“双方退回”指未使用的预算退回，不回收已经有效支付的劳动报酬。
4. localStorage 截图在刷新后保留，界面如实说明；结清 7 天后下次读取惰性删除。申诉未结清不删除。与文档“刷新即消失”的矛盾说法相比，选择可重现、可审核的本地持久化。
5. 模拟时钟只前进，不修改系统时间。3 个工作日是运营处理目标，原型显示已等待时长，不伪装成自动裁决规则；49 小时按钮用于自动审核演示。
6. 自动通过奖励可在 7 天内由发布者提请介入。回滚若遇答题者可用不足则原子失败，保留待处理，不强制制造负余额。管理员需说明调账依据后另行处理，调账始终留痕。
7. 链接只检查格式和规范化查重；原型不声称能检测第三方服务器可达性。提供链接失效报告。

  async function readFile(file) {
    if (!file) return;
    const status = $('#upload-status');
    currentProof = null; $('#proof-preview').hidden = true;
    if (!['image/png', 'image/jpeg'].includes(file.type) || file.size > 5 * 1024 * 1024) { status.textContent = '请选择一张不超过 5MB 的 JPG 或 PNG 图片。'; return; }
    status.textContent = '正在读取并压缩图片…';
    const targetInput = $('#proof-file');
    try {
      const bitmap = await createImageBitmap(file), canvas = document.createElement('canvas');
      const scale = Math.min(1, 960 / Math.max(bitmap.width, bitmap.height)); canvas.width = Math.max(1, Math.round(bitmap.width * scale)); canvas.height = Math.max(1, Math.round(bitmap.height * scale));
      const ctx = canvas.getContext('2d'); ctx.fillStyle = '#ffffff'; ctx.fillRect(0, 0, canvas.width, canvas.height); ctx.drawImage(bitmap, 0, 0, canvas.width, canvas.height); bitmap.close();
      const data = canvas.toDataURL('image/jpeg', .72);
      if (targetInput !== $('#proof-file') || !$('#dialog').open) return;
      if (data.length > 900000) throw new Error('压缩后的图片仍过大，请裁剪后重试。');
      currentProof = data; $('#proof-preview').src = currentProof; $('#proof-preview').hidden = false; status.textContent = '图片已准备好，确认隐私提示后即可提交。';
    } catch (error) { if (status.isConnected) status.textContent = error.message || '图片无法读取，请换一张有效图片。'; }
  }

  function normalizeLink(value) {
    let url;
    try { url = new URL(String(value).trim()); } catch { fail('请输入完整的 http 或 https 问卷链接。'); }
    ensure(['http:', 'https:'].includes(url.protocol) && !url.username && !url.password, '链接必须以 http:// 或 https:// 开头，且不能包含账号密码。');

    url.hash = '';
    for (const key of [...url.searchParams.keys()]) if (/^(utm_|fbclid$|gclid$|spm$)/i.test(key)) url.searchParams.delete(key);
    url.searchParams.sort();
    // HTTP and HTTPS point to the same survey identity; preserve meaningful query ids.
    return url.hostname.toLowerCase().replace(/^www\./, '') + (url.port ? ':' + url.port : '') + url.pathname.replace(/\/+$/, '') + url.search;
  }
  function platform(link) {

  function entry(s, userId, availableDelta, frozenDelta, type, note, taskId = null, submissionId = null, counterparty = '系统') {

  function updateTask(s, t) {

    if (t.deadline <= s.now) t.stopped = true;
    const reserved = taskSubs(s, t.id).some(x => isReserved(x, s.now));
    if (t.status === 'removed') { if (!reserved) refund(s, t); return; }

      t.status = reserved ? 'settling' : 'closed';
      if (!reserved) { t.closedAt = s.now; refund(s, t); }
    } else t.status = remaining(s, t) === 0 ? 'settling' : 'open';
  }

  function assertState(s) {

      ensure(u.frozen === s.tasks.filter(t => t.publisherId === u.id).reduce((sum, t) => sum + t.escrow, 0), '任务冻结余额校验失败。');

      ensure(u.frozen === s.ledger.filter(x => x.userId === u.id).reduce((sum, x) => sum + x.frozenDelta, 0), '冻结积分流水校验失败。');
    }
    ensure(new Set(s.submissions.map(x => `${x.taskId}:${x.userId}`)).size === s.submissions.length, '重复领取校验失败。');

    }

  }

const http = require('node:http');
const fs = require('node:fs');
const path = require('node:path');
const root = path.resolve(__dirname, '../prototype');
const port = Number(process.env.PORT || 4173);
const types = { '.html': 'text/html; charset=utf-8', '.js': 'application/javascript; charset=utf-8', '.css': 'text/css; charset=utf-8', '.json': 'application/json; charset=utf-8' };
http.createServer((req, res) => {
  let file;
  try { const name = decodeURIComponent(new URL(req.url, 'http://localhost').pathname); file = path.resolve(root, '.' + (name === '/' ? '/index.html' : name)); } catch { res.writeHead(400).end('Bad request'); return; }
  if (!file.startsWith(root + path.sep)) { res.writeHead(403).end('Forbidden'); return; }
  fs.readFile(file, (error, data) => {
    if (error) { res.writeHead(404, { 'Content-Type': 'text/plain; charset=utf-8' }).end('页面不存在，请回到 http://localhost:' + port); return; }
    res.writeHead(200, { 'Content-Type': types[path.extname(file)] || 'application/octet-stream', 'Cache-Control': 'no-store', 'X-Content-Type-Options': 'nosniff' }); res.end(data);
  });
}).listen(port, '127.0.0.1', () => console.log(`问问本地预览：http://127.0.0.1:${port}`));

# 问问 · 校园问卷互助演示

双击同目录的 `campus-helper-demo.html` 即可体验，无需安装环境。账号和积分均为本机模拟数据。

## 推荐演示顺序

1. 右上角选择小林，初始可用 100 分。发布 10 分 × 8 份问卷，链接可填 `https://surveys.example/my-study`。
2. 小林可用变为 20、冻结变为 80；再填超预算任务，观察差额提示和禁用按钮。
3. 头像切换阿哲，在大厅领取刚发布的任务，再点击打开问卷。
4. 回来提交截图；可生成明确标注的演示证明，勾选隐私确认。只提交不立即发奖。
5. 切回小林，从“我的任务”审核；通过后阿哲 +10，小林冻结 -10。
6. 首份证明存疑时选择原因，转管理员复核。切到管理员，通过头像进入后台，填写裁决理由。
7. 要演示普通拒绝，先通过首份，再让另一账号提交第二份。拒绝必须选原因；答题者可在 7 天内申诉。
8. 头像菜单推进 49 小时可演示自动通过，推进 25 小时可演示未提交领取释放。
9. 管理员后台包含申诉队列、任务管理、用户管理和数据看板；所有积分统计来自当前流水。
10. “重置演示数据”恢复初始状态，清除自建问卷、截图和积分变更。

## 与方案 v2 的两个关键差异

- 首次发布的首份证明不能直接拒绝，存疑转管理员，以遵守文档的首份保护规则。
- 被拒绝后奖励和名额保留 7 天；申诉期满或裁决维持拒绝才释放，避免名额超卖和申诉发奖缺口。

## 数据边界

刷新后同一浏览器保留数据；截图仅保存本地缩略图，结清 7 天后下次读取清理。换浏览器、换文件位置、file/HTTP 切换或清理存储可能产生不同数据空间。请勿上传真实个人信息。

当前无真实账号、服务器、跨设备同步、邮件、支付或问卷答案采集。外部链接仅格式校验和查重，可手动报告失效。真实访谈与用户试点仍需团队组织；原型不代表产品假设已通过验证。

源码在项目的 prototype 目录，启动命令 `node scripts/serve.cjs`；重建交付文件 `node scripts/build.cjs`；规则测试 `node --test tests/model.test.cjs`。尚未提交或推送 GitHub。
